# 패턴 재설계 (소매 캡/암홀 형상)

## 배경
`sleeve-redesign-B.md`(독립 소매 패널, 구현 1~6번)는 완료됐고, 남은 문제는
어깨-소매 접합부 톱니였다. 그동안 접근은 봉제선 제약(이즈인/직접스냅) 쪽
튜닝이었다 — 이번 세션에서 그 접근의 한계가 실측으로 드러났다.

## 오늘 실측 (sleeveSeamCheck, chest-width-50.png, 품55cm)

- 어깨 코너(k0/k11, 이즈인 구간): 6.3~7.2mm — 목표(3cm)보다 훨씬 작고 회귀 아님
- **코너 인접 열(k1/k10, 직접스냅 구간)이 코너 자체보다 더 벌어짐**: 14.2~17.7mm
  (left k1=17.7mm k10=14.2mm / right k1=17.2mm k10=6.8mm)
- 즉 톱니의 최대치는 코너(k0/k11)가 아니라 그 바로 옆 — 이즈인을 코너에서
  k1/k10까지 넓혀도 근본 해결이 아닐 가능성 (땜질을 옆으로 옮기는 것뿐)

## 넥라인 시접 — 별개 확인 (같은 세션)
`addNecklineSeamConstraints`(buildGarmentSim.ts:1088)도 `pinCorners`보다
먼저 restLength를 캡처해 코너와 같은 재배치-타이밍 패턴을 갖지만, 몸통 열은
앞/뒤 row0 양쪽이 다 핀 처리되고 `clothPhysics.ts:257`
(`if (pinnedA && pinnedB) continue;`)가 그 제약을 완전히 스킵해 무해함을
코드로 확인함. 넥라인은 이 조사에서 제외.

## 오늘 나온 방향 (가설, 미착수)
k1/k10이 코너보다 더 벌어진다는 건 "제약 강도(이즈인 계수)" 문제가 아니라
**소매 패턴 자체(암홀 곡선 shape, 소매 캡 shape)가 몸판 암홀 곡률과 안 맞는다**는
신호일 수 있다. 다음에 볼 것:
1. k=1, k=10에 대응하는 몸판 암홀 좌표(front row1 / back row1)와 소매 링
   좌표 간 실제 곡률(각 k의 인접 3점 각도) 비교 — 이즈인 계수를 더 만지기
   전에 형상 자체부터 확인
2. `layoutSleevePanel`이 소매 단면을 배치할 때 쓰는 각도 분배(12정점 균등
   분배)가 몸판 암홀의 실제 곡률 분포(코너~겨드랑이 사이 곡률이 균일하지
   않음, sleeve-redesign-B.md 실측 참고)와 맞는지 재검토
3. 필요하면 소매 링 정점 분배를 몸판 암홀 곡률에 맞춰 재표본화(현재는
   "재표본화 불필요"로 결론났던 항목 — 이번 실측으로 재검토 대상)

## 하네스 (scripts/paramSweep.ts)
품×소매통 조합을 자동으로 돌려 관통량/봉제선갭/톱니(seamNormalJaggedness)를

`src/lib/seamDiagnostics.ts`(`ringJaggedness`)로 빼서 Garment.tsx의
브라우저 디버그(`window.__fitDebug.seamNormalJaggedness()`)와 공유.

## 1. 소매산 곡선 표준 공식 (조사)
web search 종합 (출처: [Threads Magazine](https://www.threadsmagazine.com/project-guides/fit-and-sew-tops/on-fitting-sleeves), [Dresspatternmaking](https://dresspatternmaking.com/blog/understanding-the-sleeve-part-3), [Sparrow Refashion](https://sparrowrefashion.com/2024/04/23/basic-sleeve-pattern-drafting-simplified-a-beginners-guide/)):

- **이즈량(암홀 둘레 대비 소매산 둘레)**: 우븐 1.5~2.5cm, 니트 0.5~1.5cm,
  아우터 +3.8~6.4cm(둘레는 bicep 쪽). "핏된 소매"는 3~4.5cm까지도 언급됨.
  우리는 원단 구분 없이 **3cm 고정값**으로 시작(우븐 평균, 중간값) — 원단별
  분기는 나중 항목.
- **소매산 높이**: "삼각형 관계" — 세 변(암홀 둘레, bicep 폭, 캡 높이) 중
  둘을 알면 나머지가 결정됨. 표준 삼각법: `capHeight = sqrt(hyp² - base²)`,
  `hyp = (암홀 둘레 + 이즈량) / 2`, `base = bicep 폭 / 2`. 대략치 공식(더
  단순한 버전)도 있음: `capHeight ≈ 암홀둘레/3 + 여유 1cm`.

## 2. 우리 데이터로 입력값 확보 확인
- **암홀 둘레**: `armholeRingVertices(sim, PANEL_FRONT, PANEL_BACK, col, armholeStartRow)`가
  실좌표 12점을 그대로 반환(buildGarmentSim.ts:890) — 인접점 거리 합(+wrap)으로
  cm 단위 둘레를 바로 계산 가능. **확보됨.**
- **소매통(bicep)**: `sleeveWidthM` 파라미터 — `layoutSleevePanel`에 이미
  들어옴. **확보됨.**
- **소매길이**: `arm.length`(`ArmDir.length`) — 역시 이미 들어옴. **확보됨.**
- 결론: 표준 공식에 필요한 입력 전부 새 계산/새 파라미터 없이 이미
  `layoutSleevePanel` 함수 시그니처 안에서 구할 수 있음 — 함수 밖으로
  나갈 필요 없음(소매 전용 범위 유지에 유리).

## 3. 2D → 3D 매핑 설계
`layoutSleevePanel`(buildGarmentSim.ts:920)은 이미 2D 패턴 개념을 일부
쓰고 있다 — 열(k)은 "둘레 위치"(각도), 행(r)은 "팔 축을 따라 얼마나
갔는지"(reach)로 분리돼 있음. 문제는 각도 공식이
`angle = π/2 - k*(2π/ringCols)`로 **균등 분배**라는 것 — 실제 암홀은
어깨점~겨드랑이 구간 곡률이 균일하지 않은데, 이 균등 각도가 row0(정확히
슬릿 위치, blendT=0)에서 row1로 넘어가는 순간 갑자기 "이상적 균등원"
방향으로 꺾여버려 법선이 급변한다(=톱니, seamNormalJaggedness가 잡는 값).

설계:
- **각도**: `armholeVertex`의 인접 거리 누적합(cm, wrap 포함)으로 각 k의
  호장 비율(`cum[k]/total`)을 구하고, `angle = π/2 - (cum[k]/total)*2π`로
  대체 — 실제 암홀 곡률 분포를 그대로 반영. k=0(어깨점)이 90°인 기존
  관례는 유지.
- **반지름(캡 둘레)**: 지금은 `targetRadius`가 행(r)과 무관하게 상수
  (`computeArmTubeRadius(sleeveWidthM)`) — 암홀 실측 둘레와 무관하게
  사용자가 정한 소매통만 반영해, 이음매 근처에서도 "정상 소매 굵기"를
  요구해 실측 암홀과 어긋날 수 있음. row0 근처(캡 구간)만 표준 공식의
  `capRadius`(암홀 둘레+이즈/2π)를 쓰고, 캡 구간을 벗어나면 기존
  `computeArmTubeRadius(sleeveWidthM)`로 부드럽게 전환.
- **캡 높이 → 램프 길이**: 삼각법으로 구한 `capHeightCm`를 소매길이 대비
  비율로 환산해 "캡 구간이 몇 행까지인지"(`capRampT`)를 정한다 — 지금
  하드코딩된 공유 상수 `ARM_TUBE_RADIUS_RAMP_T`(0.3, 구 플랩과 공유)는
  건드리지 않고, `layoutSleevePanel` 로컬 전용 값을 새로 계산해 쓴다(구
  플랩에 영향 없음 = 몸판/기존 시스템 무변경 유지).
- 이 세 가지 모두 `layoutSleevePanel` 함수 **안에서만** 계산 가능(새 파라미터
  불필요) — 함수 시그니처 불변, 파일 하나(buildGarmentSim.ts) 안에서 끝남.

## 4~5. 시범 구현 + 검증 — 3가지 가설 전부 기각 (실측, 코드 원복)
`layoutSleevePanel`(buildGarmentSim.ts, 소매 전용 함수, 몸판 무변경)에
아래 세 버전을 순서대로 구현·측정. 매번 `npm run sweep:pattern`(Node
하네스) + 브라우저 `seamNormalJaggedness()` 둘 다 확인.

**베이스라인(현재 코드, 회귀 없음 확인용)** — 두 하네스가 서로 다른 수치를
낸다는 것부터 확인해둠(자체충돌/메시충돌 등을 뺀 Node 하네스가 원래
구조적으로 더 나쁘게 나옴, checkSleeveSeam.ts 주석에 이미 문서화된 한계):
- Node(`sweep:pattern`, 대표 포즈 1개): sleeve 102.2~164.7°
- 브라우저(`seamNormalJaggedness`, chest-width-50.png 업로드): sleeve
  77.02~82.76°, armhole 106.88~110.78°

**시도 1 — 각도를 호장 비율로 재배분 + 캡 구간 반지름을 암홀 실측
둘레+이즈로**(문서 "3. 2D→3D 매핑 설계"에 적은 원래 계획 그대로 구현):
- Node: sleeve 109.6~154.6° (베이스라인 대비 대부분 악화, 0.65 조합만 개선)
- **기각.**

**시도 2 — 반지름 롤백, 각도만 호장 비율로(이즈/캡 개념 제거, 각도만
분리 검증)**:
- Node: sleeve 108.4~158.2° — 시도 1보다도 나쁨. 각도 재배분 자체가
  범인임을 확인.
- **기각.**

**시도 3 — 각도를 아예 재배정하지 않음(균등도 호장비율도 아님): 각 k는
center 기준 자기 슬릿 위치의 실제 각도(atan2)를 그대로 쓰고, 반지름만
슬릿 실측값→목표값으로 블렌드(순수 방사형 변형)**:
- Node: sleeve 106.6~155.5° — 여전히 베이스라인보다 나쁨.
- **브라우저(실측)도 확인**: armhole 107.94~113.39°(베이스라인과 비슷,
  회귀 아님 — 예상대로 몸판 쪽은 거의 영향 없음), **sleeve
  132.37~141.28°(베이스라인 77~83°보다 뚜렷이 악화)**.
- **기각.**

**결론**: 세 가설(균등 각도가 문제 / 호장비율로 고치면 됨 / 각도 재배정
자체를 없애면 됨) 전부 실측에서 베이스라인보다 나빠졌다 — "각도를 어떻게
배분하는가"는 톱니의 진짜 원인이 아니었거나, 최소한 이 세 가지 변형으로는
못 잡았다. 관통량/봉제선갭은 세 시도 모두 회귀 없음(위험 신호 아님) —
잡힌 건 목표 지표(jaggedness)뿐이라 "위험 신호"에는 안 걸렸지만 성공
기준(20° 이내, 개선)에는 전혀 못 미쳤다. **`layoutSleevePanel` 코드는
원래대로 원복함(git checkout) — 커밋 안 함.**

## 다음 가설 (미착수, 다음 세션 시작점)
세 시도 모두 "row0(슬릿, 정확)에서 row1로 넘어가는 순간 각도를 강제로
바꾼다"는 공통점이 있었다(시도3도 반지름만 바꾼다지만 각도를 atan2로
고정한 것 자체가 여전히 "재계산"이지, row0→row1 사이 실제 이웃 정점과의
상대 곡률 연속성을 보장하진 못함). 다음에 볼 것:
1. row0 자체의 곡률(인접 k끼리의 실제 각도 변화율, 이미 doc 초반의
   "겨드랑이 5.54cm vs 어깨 0.20cm" 실측이 이 곡률이 극단적으로 불균일함을
   보여줌)을 row1이 그대로 이어받는 "탄젠트 매칭"(에르미트 블렌드류) 시도 —
   position만 맞추는 lerp가 아니라 derivative(방향)도 row0에서 맞추기.
   지금 세 실패 시도는 전부 "position은 lerp, 각도/반지름 목표는 새로
   계산"이라 derivative 불연속이 여전히 남아있었을 가능성이 큼.
2. seamNormalJaggedness 자체가 재는 게 "row0→row1 사이 법선"인지 다시
   확인 — computeVertexNormals()가 row0 법선을 계산할 때 실제로 어떤
   이웃(row1만? row1+col 이웃까지?)을 쓰는지 정확히 짚고 나서 접근할 것.
3. 이번 세션 다 실패한 세 변형(각도 재배분류) 방향은 재시도하지 말 것 —
   시간 낭비 확인됨.

## 6. 탄젠트 매칭 가설 — 1번(방향 어긋남 실측) 완료, 가설 강하게 확인됨
`window.__fitDebug.sleeveRow0TangentCheck()` 추가(Garment.tsx, 코드 변경
없이 순수 측정 — frontPositions/backPositions/sleevePositionsLeft/Right만
읽음). 몸판 쪽 탄젠트는 같은 행(row)에서 암홀 열(xMin/xMax)과 그 바로
바깥 열(xMin-1/xMax+1, 구 플랩 열 — 아직 살아있어 항상 존재)을 잇는
방향(표면이 이음매를 넘어 계속됐다면 향했을 방향의 근사), 소매 쪽
탄젠트는 row0→row1 방향.

right diffsDeg: [151.6, 154.4, 125.1, 104.5, 84.4, 166.0, 20.2, 129.0, 89.4, 109.9, 151.5, 157.8]

12개 중 대부분이 75~166° — 거의 직각~정반대 수준으로 어긋나 있음(k=6
부근만 예외적으로 작음, left 6.62°/right 20.19° — 겨드랑이 쪽만 우연히
방향이 맞아떨어짐). **가설 강하게 확인됨: row0에서 소매가 뻗어나가는
방향이 몸판 표면이 이어졌을 방향과 대부분 크게 어긋나 있다.** 세 번의
"각도 재배분" 시도가 전부 실패한 이유와 정합적 — position만 lerp로
맞추고 방향(도함수)은 매번 새로 계산된 목표(균등원/호장비율원/atan2)를
썼으니, 애초에 몸판 쪽 방향과 맞을 이유가 없었다.

**다음 단계(2번, 미착수)**: row0 위치는 그대로 유지하고, 소매가 row0에서
뻗어나가는 **초기 방향**을 위 torsoTangent와 맞추도록 에르미트 블렌드류로
조정 — 세부 설계와 구현은 다음 세션.

## 7. 방향 전환 — 파라미터 미세조정 중단, 2D 패턴 조각 방식으로 재설계
탄젠트 매칭(6번)을 실제로 구현하기 전에 사용자가 방향을 바꿈: 지금까지
네 번(각도+반지름, 각도만, 방향 유지+반지름만, 탄젠트 측정)의 시도가
전부 "같은 함수(슬릿을 팔 방향으로 압출) 안에서 파라미터만 바꾸는"
미세조정이었다는 게 공통 한계 — `layoutSleevePanel`을 고치는 대신
통째로 대체한다. CLO3D류 워크플로(2D 패턴 조각을 대략 배치 → 봉제선
제약 → 물리가 드레이프)를 따른다.

### 설계
**핵심 발상 전환**: row0을 더 이상 `armholeVertex[k]`와 대수적으로
정확히 일치시키지 않는다(6번까지의 모든 버전이 유지하던 불변식을 깬다).
대신 `addSleeveArmholeSeam`(그대로 재사용, restLength=SEAM_REST_LENGTH
=6mm)이 row0을 실제 암홀 쪽으로 "봉제선 당기듯" 서서히 끌어당기게 둔다 —
CLO3D 등 실제 3D 개러먼트 시뮬레이터가 2D 패턴 조각을 정확히 붙여넣지
않고 대충 옆에 놓은 뒤 시뮬레이션이 봉제선을 따라 붙이는 것과 같은 방식.

**2D 패턴 → 3D 배치**:
- **반지름**: 모든 행(r)·모든 열(k)에서 상수 `targetRadius`
  (`computeArmTubeRadius(sleeveWidthM)`, 기존 그대로) — 완전한 원통.
  옆선이 저절로 직선이 된다(원통의 모선 = 직선).
- **각도**: 균등 분배(`angle = π/2 - k·2π/ringCols`, k=0=어깨점=위쪽) —
  4번의 실패로 "호장비율/atan2 재배정"은 이미 기각했으니 제일 단순한
  균등을 그대로 씀.
- **소매산(캡) 굴곡 — 유일하게 새로 쓰는 부분**: row0의 "팔 축 방향
  오프셋"(reach)을 k의 각도 위치에 따라 다르게 준다. 어깨점(k=0, top)
  에서 `capHeightCm`(표준 공식: `capHeight=√(hyp²-base²)`,
  `hyp=(암홀둘레+이즈3cm)/2`, `base=소매통/2` — 1번 조사 그대로 재사용)
  만큼 몸쪽으로 볼록, 언더암(top에서 각도 180° 떨어진 지점, k≈ringCols/2)
  에서 0으로 떨어지는 반코사인 굴곡(`capBulge(k) = max(0,cos(angFromTop))
  · capHeightM`) — 어깨는 볼록하고 겨드랑이 쪽은 평평한 실제 소매산
  모양의 거친 근사.
- **행(r) 방향 — 소맷부리는 직선**: v=r/(ringRows-1)에서
  `reach(k,v) = arm.length·v − capBulge(k)·(1−v)` — v=0(row0)에서는
  캡 굴곡 그대로, v=1(소맷부리)에서는 k와 무관하게 `arm.length`로 수렴
  (평평한 소맷부리, 요청사항 그대로).
- 제거: `blendT`/`tubeRadiusScale` 기반 슬릿→이상원 lerp 전체, 슬릿
  기준 반지름/각도 측정 전체 — 더 이상 armholeVertex의 각 k별 실제
  좌표를 읽어서 계산에 쓰지 않는다(center만 재사용 — 배치 기준점으로만).
  `tubeRadiusScale`/`ARM_TUBE_RADIUS_RAMP_T` 등 공유 상수는 구 플랩이
  계속 쓰므로 안 건드림(호출만 제거).

이 배치는 row0에서 실제 암홀과 몇 cm~수십 mm 어긋난 채 시작한다 —
의도된 것이고(대략 배치), `addSleeveArmholeSeam`이 매 프레임 그 갭을
좁히는 게 검증 대상이다(봉제선갭 지표로 확인).

## 8. 검증 — 소매 쪽은 실측 개선, 전체 목표(20°)는 armhole 성분이 막음

**변형 A(위 설계 그대로, row0도 대략 배치)** — 브라우저 실측
(chest-width-50.png, 품55, +4s/+11s 둘 다 동일 → 완전히 정착된 값):
```
sleeveLeft  max: 60.64° → 67.8°(재측정, 변동폭 내)   (베이스라인 77.02~82.76°)
sleeveRight max: 62.29° → 57.51°(재측정)              (베이스라인 그대로)
armholeLeft/Right: 89.87~108.59°                      (베이스라인 106.88~110.78°, 거의 그대로)
```
**소매 쪽 톱니가 베이스라인보다 뚜렷이·재현 가능하게 개선됨**(약 20~25%
감소, 여러 번 재측정해도 안정적). 봉제선갭(`sleeveSeamCheck`)은 0.2~2.6cm
(코너 0.72cm 유지) — 베이스라인과 같은 자릿수, 회귀 아님. 관통량
(paramSweep)도 베이스라인과 같거나 일부 조합에서 개선(예: 품50/소매통14
62.75→54.83mm). **위험 신호 없음.**

**변형 B(row0만 armholeVertex로 고정, 나머지는 A와 동일)** — "시접 갭 0
불변식을 지키면서 나머지만 바꾸면 더 낫지 않을까" 가설로 시도, 실측
결과 **더 나쁨**(sleeveLeft 102.69°, sleeveRight 73.52° — A보다 확실히
악화). row0을 실제 암홀 형태(불규칙 다각형)로 고정하는 순간 곧바로 옆
행과의 불연속이 재현되는 것으로 보임 — A(row0도 대략 배치, 물리가
당겨 붙이게 둠)가 더 나은 이유와 정합적. **A를 채택, B는 기각.**

**armhole 성분(89.87~110.78°)은 다섯 가지 소매 전용 변형(4번 문서의
세 번 + 이번 A/B) 전부에서 거의 안 움직였다** — 이건 몸판(front/back
패널) 자체의 메쉬 곡률(어깨 wrap 지점의 실제 기하학적 접힘)에서 나오는
값이라, 소매 쪽 코드만으로는 못 건드리는 게 구조적으로 당연해 보인다.
`seamNormalJaggedness`의 "전체 목표 20°"는 `max(armholeLeft, armholeRight,
sleeveLeft, sleeveRight)`라 armhole 성분이 안 움직이는 한 소매를 완벽하게
고쳐도(0°) 전체 목표는 못 채운다.

**판단 필요(갈림길)**: 소매 쪽은 5번 시도 중 최선(A)으로 실측 개선을
달성했고 위험 신호는 없다. 하지만 **전체 20° 목표는 몸판 코드를 건드리지
않는 한 도달 불가능해 보인다** — 이건 판정 기준의 위험 신호("몸판 코드
수정 필요")와 사실상 같은 지점이라 여기서 멈추고 보고한다. 계속하려면
범위를 몸판(어깨 wrap 지점 자체 곡률)까지 넓힐지 사용자 판단이 필요.

## 9. 소매 재설계 완료 (2D 패턴 방식) — 결론
`layoutSleevePanel`을 슬릿-압출-블렌드 방식에서 2D 패턴 조각 방식으로
전면 교체. row0을 암홀과 대수적으로 강제 일치시키지 않고 물리 봉제선이
끌어당기게 함. 소매 톱니 77~83°→57~68° 개선, 회귀 없음.

## 10. armhole 성분은 별개 이슈로 분리 (결정)
`seamNormalJaggedness`의 armhole 성분(90~111°)은 몸판 표면 자체의
곡률(저해상도 12점 표현)에서 오는 것으로, 다섯 번의 소매 전용 시도
내내 전혀 안 움직임 — 소매 문제가 아니라 몸판 격자/곡률 표현 문제.
화면상 만족스러우면 이 잔여치는 실질적 결함 아님. 다룰 경우 별도
범위(몸판 해상도 또는 곡률 근사 방식)로 착수할 것.

## 11. 화면 확인 결과 (3c19279 이후)
지표 개선(row0 톱니 57~68°)에도 불구하고 화면상 소매 형태는 이전과
크게 다르지 않음 — 여전히 각진/어색한 형태. 자체 리뷰에서 예측한 대로
row0 지표 개선이 소매 전체 자연스러움을 보장하지 않음이 확인됨.

한도 복구 후 다음 세션 시작점: row3~8 구간을 포함하는 지표 확장부터.
그 지표로 실제 문제 위치를 다시 특정한 뒤 수정.

## 12. 지표를 row0~11 전체로 확장 — row3~8도 실제로 심하게 톱니, 원인은 layoutSleevePanel이 아니라 물리 전파

**구현**: `ringJaggedness()`는 그대로, 두 호출부만 row0 하드코딩을 풀어
0~11 전체를 훑도록 확장.
- `scripts/paramSweep.ts`: `sleeveRingNormalsAt(attr, row)`에 row 인자
  추가, `ComboResult.sleeveRowsMaxDeg: number[]`(행별 좌/우 중 큰 값,
  12개) 신설. `sleeveJaggednessDeg`는 이 배열의 최댓값(기존 20° 목표와
  같은 정의 유지). 콘솔에 조합별 12행 배열도 별도 출력.
- `src/components/Garment.tsx`(`window.__fitDebug.seamNormalJaggedness`):
  기존에 이미 `sleeveRingNormals(geometry, row=0)`가 row 인자를 받게
  돼 있었음 — 호출부만 0~11 루프로 바꿔 `sleeveLeftRows`/`sleeveRightRows`
  (12개씩) + `sleeveLeftMax`/`sleeveRightMax` 반환. 기존
  `sleeveLeft`/`sleeveRight`(단일 값) 키는 제거(다른 코드에서 참조하는
  곳 없음, grep 확인).
- 몸판/공유 상수 무변경, `npx tsc -b` 클린.

**재측정(`npm run sweep:pattern`, 12조합, Node 하네스)**: 대표값
(품55/소매통18, row0~11):
```
[133.9, 146.5, 177.7, 163.1, 156.9, 147.0, 152.7, 166.9, 171.5, 168.8, 160.2, 152.3]
```
12조합 전체에서 공통 패턴: row0(캡)이 최댓값인 경우는 거의 없고, row2와
row7~9 부근에서 최댓값이 자주 나옴(예: 품60/소매통14 row3=174.5가 최댓값,
품65/소매통18 row7=176.4가 최댓값). row3~8 구간 값이 row0보다 낮은 경우는
드묾 — **row3~8도 row0 못지않게, 종종 더 심하게 톱니짐. 새 톱니가 아니라
기존 row0-only 지표가 놓치고 있던 톱니**(YES).

(참고: Node 하네스 절대값은 문서 8/9번의 브라우저 실측치(row0
57~68°)보다 구조적으로 높다 — 4번 문단에 이미 기록된 Node vs 브라우저
괴리, 자체충돌 등 하네스 차이 때문. 상대적 행별 패턴 판단에는 영향 없음.)

**원인 특정(3a 시도) — layoutSleevePanel 자체는 무죄로 확인, 진범은
`addSleeveArmholeSeam`발 왜곡의 물리 전파**:
`layoutSleevePanel`의 `reach(k,v) = arm.length·v − capBulge(k)·(1−v)`를
분석하면, capBulge(k)로 인한 링 형상 왜곡은 가중치 `(1−v)`가 곱해져
row0(v=0)에서 최대, row11(v=1, 소맷부리)에서 0으로 선형 감쇠하도록
설계돼 있다 — 즉 정적 배치만 보면 왜곡이 row0에 집중되고 아래로 갈수록
줄어야 정상.

이를 실측으로 확인하기 위해 임시 진단 스크립트(1회성, 저장 안 함)로
물리 스텝 0회(레이아웃 직후)와 이후 프레임의 row별 톱니를 비교(품55/
소매통18):
```
frame0(레이아웃 직후, 물리 0스텝): [60,60,60,60,60,60,60,60,60,60,60,60]  ← 완전 균일
frame1(물리 1스텝):     [170.9,163.3,109.1,92.7,80.6,76.5,69.5,68,66.2,65.9,66.1,67]
frame5:                 [147.9,148.8,140.7,162.7,166.8,98.7,91.8,82.4,69.7,64.8,61.4,59.1]
frame180(정착):         [133.9,146.5,177.7,163.1,156.9,147.0,152.7,166.9,171.5,168.8,160.2,152.3]
```
**frame0은 12행 전부 정확히 60°(정12각형 기둥, 왜곡 없음)** — 즉
`layoutSleevePanel`의 reach/capBulge 블렌드는 톱니를 만들지 않는다(가설
기각). 물리 스텝을 단 1번만 밟아도(frame1) row0~2가 즉시 100~170°대로
튀고, 이후 프레임을 거치며 그 왜곡이 row3~8까지 번져 정착값(frame180)에
이른다.

메커니즘: `addSleeveArmholeSeam`(buildGarmentSim.ts:1062)이 소매 row0을
몸판 암홀 다각형(그 자체가 저해상도 12점이라 90~111° 고유 톱니를 가짐,
10번 문단에서 이미 out-of-scope로 분리한 값)에 restLength 6mm(코너는
0.6mm)로 잡아당긴다. 이 row0의 불규칙한 형태가 원통형 소매 튜브의 구조적
제약(그리드 엣지, `addSleeveWrapConstraint`의 랩 엣지 포함)을 통해
row3~8까지 감쇠되지 않고 전파된다 — SLEEVE_RING_ROWS=12로는 이 전파를
막을 별도의 "행별 원형 유지" 제약이 없다.

**결론**: row3~8 톱니는 실재하고 크지만, 원인은 `layoutSleevePanel`의
행 보간 로직(reach/capBulge)이 아니라 `addSleeveArmholeSeam`이 유발한
row0 왜곡이 물리 솔버를 통해 아래로 전파되는 현상이다. 근본 수정은
(i) row0을 당기는 힘을 약화/스무딩하거나 (ii) 소매 튜브에 행별 원형
유지 제약을 추가하는 방향일 텐데, 둘 다 이 세션 범위(진단)를 넘는 실제
구현이라 착수하지 않음. 또한 왜곡의 뿌리(암홀 다각형 자체의 저해상도
불규칙성)는 10번 문단에서 이미 "몸판 쪽 문제, 소매 전용 코드로는 못
건드림"으로 분리해둔 것과 같은 근원이다.

**위험 신호**: 없음. `layoutSleevePanel`/body 패널 코드 수정 없음(진단만,
1회성 스크립트는 실행 후 삭제), 관통량/봉제선갭 변화 없음(코드 변경이
지표 계산부뿐이라 물리 결과 자체는 동일), `npx tsc -b` 클린.

## 16. 암홀 링 12점→24점 스플라인 리샘플링 — 구현, maxSeamGapCm 회귀 확인, 완화 시도 기각

**완화 시도(`/safe-experiment`) — 기각**: 중복 쌍(2i↔2i+1, row0만)
구조 제약만 `scaleConstraintStiffness`로 완화(`SLEEVE_STIFFNESS_AT_TIP`
패턴 재사용), 나머지 링 구조는 그대로 둠. 목표: `maxSeamGapCm`이
베이스라인(0.72cm 부근)으로 복귀.
```
factor=0.4: maxSeamGapCm 1.29~1.45cm (거의 무변화)
factor=0.3: maxSeamGapCm 1.25~1.45cm (거의 무변화)
```
0.4/0.3 모두 무처리(1.32~1.56cm) 대비 유의미한 개선 없음 — 이 특정
엣지(중복 쌍 구조 제약)는 병목이 아니었던 것으로 결론. `/safe-experiment`
기준(목표 미달 시 원복) 적용 — `dampenSleeveDuplicateSeamPairs` 함수와
호출부 제거, 코드는 1:2 매핑 상태(리샘플링+addSleeveArmholeSeam 수정)로
복귀. 커밋 없음.

**결론**: 12→24 리샘플링 자체(코드, tsc 클린)는 유지 상태로 남아있지만
`maxSeamGapCm`이 목표 범위(0.59~0.72cm)에 못 미침 — 병목이 중복 쌍
엣지가 아니라면 다른 원인(전체 PBD 반복 횟수 부족, 코너 이즈인 자체의
간격, 또는 애초에 1:2 중복 매핑 구조 자체의 한계) 가능성. 다음 결정
지점: (a) 짝수 컬럼만 직접 시접(문서에서 먼저 기각했던 옵션)으로 다시
시도, (b) PBD 반복 횟수/서브스텝 자체를 늘려보는 실험, (c) 목표를
1.5cm대로 낮춰 수용, 사용자 판단 필요.

**옵션(a) 재시도(`/safe-experiment`) — 성공**: 짝수 컬럼(k=2·rawK)만
raw 점에 직접 시접, 홀수 컬럼(k=2·rawK+1)은 시접 제약 자체를 없앰(링
구조 제약으로만 자리잡음 — row1~11이 원래 시접 없이 구조 제약만으로
자리잡는 패턴을 row0 홀수 컬럼까지 확장한 것과 동일). `addSleeveArmholeSeam`/
`paramSweep.ts`의 `seamGapCm`/`Garment.tsx`의 `sleeveGridCheck`·
`sleeveSeamCheck` 전부 "짝수 컬럼 12개만 raw 점과 비교"로 통일(홀수는
애초에 시접 대상이 없어 "갭" 개념이 안 맞음 — 측정에서 제외).

실측(`npm run sweep:pattern`, 12조합):
```
maxSeamGapCm: 베이스라인 0.72cm → 0.72~0.78cm (사실상 동일)
sleeveJaggednessDeg(row0~11 최댓값, 12번 문단 방식): 베이스라인 상한 177.7°
  → 새 코드 상한 179.2° (거의 동일, 새 악화 없음 — 단 이 값 자체는
  원래도 미해결이던 문제라 "개선"은 아니고 "안 나빠짐")
armholeJaggednessDeg/maxPenetrationMm: 콤보별 ±5~10 안팎 변동, 베이스라인
  범위 안. 발산 12조합 전부 없음.
```
`maxSeamGapCm`은 목표(0.59~0.72cm 부근)를 달성. `sleeveJaggednessDeg`는
24컬럼(홀수 포함) 전체 법선 기반 지표라 홀수 컬럼이 눈에 띄게 뜯겨나가진
않았다는 간접 근거는 되지만, 홀수 컬럼 자체의 몸판까지 거리는 정의상
측정 안 함(시접 대상이 없어서) — 완전한 확인은 브라우저 육안(CLAUDE.md
방침)으로 남겨둠. `npx tsc -b` 클린. 커밋 없음(사용자 확인 대기).

## 17. 옵션2 이후 — 브라우저 실측 실패, SelfCollision 조사, 전체 원복

브라우저 sleeveSeamCheck() 재실측 결과 옵션2도 실패 확인: node 스윕(0.72~0.78cm)
과 달리 실제 앱에서는 row0 정착 갭이 최대 2.9~3.0cm로 그대로였다. 원인은
SelfCollision — seamSkipPairs가 addSleeveArmholeSeam이 실제로 만든 제약(짝수
컬럼)만 캡처해, 홀수(무제약) 컬럼이 SELF_COLLISION_MIN_DIST(5.5mm)에 걸려
몸판에서 밀려나는 것으로 추정. paramSweep.ts엔 SelfCollision 자체가 없어 이
힘겨루기가 재현 안 되고 통과했던 것 — node 스윕이 이 실패를 못 잡는 구조적
이유.

홀수 컬럼도 자체충돌 예외에 포함시키는 수정을 추가로 시도했으나 재실측값
사실상 무변화(2.9965cm) — SelfCollision이 진범이 아니었음이 확인됨.

**결론**: 4가지 독립 시도(1:2 중복매핑, 엣지강성완화, 옵션2, SelfCollision예외)
전부 목표(0.6~0.8cm) 도달 실패. 튜닝 문제가 아니라 24점 확장 설계 자체의
구조적 한계로 판단, 전체 원복(git checkout, 5파일)함. 톱니 삼각형은 여전히
미해결 — 근본 해법은 몸판(front/back) 코드 확장뿐, 다음 세션에서 각오하고
재착수하거나 현재 상태를 수용할지 결정 필요.
