## §1 표적 정의 — 도구에 넘긴 그대로

이 저장소의 실제 사례를 5종으로 적어 넘겼다.

1. **범위 리터럴이 자료를 다 못 덮는 것** — `p < 4` · `Math.min(a,b,c)` 항목 누락 ·
   배열 리터럴이 실제 개수보다 짧음 · `slice/subarray` 상한 · `length ===` · 배열 초기 크기
2. **삼킨 예외 / 빈 catch / 실패를 조용히 기본값으로 대체**(함정 25)
3. **조건이 거짓이면 아무 일도 안 하고 넘어가는 분기** — 게이트·검증·제약 적용 자리
4. **클램프·폴백이 사용자에게 안 알려지는 것**
5. **계기가 값을 못 읽었는데 0/빈값을 인쇄하는 것**

## §4 도구 한계 (도구가 스스로 적은 것 + 이 판의 확인)

- **표적 1**: 리터럴이 있는지는 잡히지만 **그 숫자가 실제 길이와 다른지는 사람이 대조**해야 한다.
  #1·#2는 `hasBand=true`로 **실제 실행해 확인**해야 최종 확정된다(정적으로는 「매우 유력」까지).
- **표적 3**: 「지금 거짓인가」는 정적으로 답해도 「과거에 참이었는가 / 조용히 사라진 처리량이
  얼마인가」는 **계측 없이는 못 잰다**(#5·#8).
- **표적 5**: `count === 0`이 실제로 발생하는지는 실행에서만 확정된다(#6·#7이 애매인 이유).
- **버려진 프로미스 · 워커 경계에서 죽는 에러**는 소스만으로 못 잡는다.
- **의존 라이브러리 내부**(three.js · three-mesh-bvh)는 범위 밖.

⟹ **P21 §1-3의 「조립 층에 남은 패널 수 고정은 없다」는 유효하다**(그 파일 안에서는).
**그러나 「조립 층」 밖의 소비 층(`PatternPreview`)에 같은 결함이 남아 있었다** —
P18 §4 표의 「소비 층」 절이 덮었어야 할 자리다.
